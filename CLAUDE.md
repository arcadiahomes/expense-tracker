# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

This is Next.js 16 (`cacheComponents` and `partialPrefetching` are on in `next.config.ts`). Check `node_modules/next/dist/docs/` before relying on remembered APIs. For example, `next/image`'s `priority` prop is deprecated in favour of `preload`, and middleware is now `src/proxy.ts`.

## Commands

```bash
npm run dev        # http://localhost:3000 (needs .env; see README)
npm run build && npm start
npm run typecheck  # next typegen && tsc --noEmit (typegen provides the global PageProps/LayoutProps types)
npm run lint
npm test           # vitest against DATABASE_URL_TEST: drops and recreates that schema each run (slow: real remote DB)
npx vitest run test/expenses.test.ts -t "keyset"   # one file / one test
npm run db:generate  # migration from src/db/schema/*; never hand-edit drizzle/
npm run db:migrate   # uses DIRECT_DATABASE_URL
npm run db:seed      # idempotent demo org; password from SEED_DEMO_PASSWORD
```

`build` and `dev` need `.env`. `DATABASE_URL` is read only by `src/db/index.ts` (server-only, lazily connected).

## Architecture

- **Data flows server → props.** `src/app/(app)/*/page.tsx` are async server components inside `<Suspense>` (required by Cache Components for request-time data). They call `requireActor()` (`src/server/session.ts`) and a function from `src/server/data/*`, then render the client view in `src/components/views/*` with plain serializable props. Filters that change server results (report filters, bill status/search, site-detail category tab) live in the URL `searchParams`.
- **Writes go through server actions** in `src/server/actions/*` (`"use server"`). They're thin: `run()` (`actions/run.ts`) resolves the actor, calls the data function, maps `ZodError`/`ValidationError`/`NotFoundError`/`ForbiddenError` to `{ ok: false, error, fieldErrors }`, and calls `refresh()` so server-rendered totals update. Client components use them with `useTransition` and show `res.error` via sonner toasts and field errors inline.
- **All business rules and authorization live in `src/server/data/*`**, which takes an `Actor` and validates its own input with the zod schemas in `src/server/validation.ts`. Never query tables from pages or actions directly; tests call these functions with fake actors (`test/fixtures.ts`).
- **Authorization** (`src/server/authz.ts`, permission table in `src/lib/permissions.ts`): tenant = organization; org owners/admins are site owners on every org site; others need a `site_memberships` row with role owner, accountant, engineer, assistant or viewer. `site:read` means the site's records (totals, budgets, everyone's expenses, bills, workers, suppliers); assistants don't have it, so every finance read refuses them. Org-wide reference data (workers, suppliers, materials catalog) goes through `requireOrgReader`; attendance, purchases, usage and labour payments need `field:record`. Check permissions, not roles: `requireSitePermission(actor, siteId, "finance:manage")` throws `NotFoundError` for invisible sites (don't leak existence) and `ForbiddenError` when the role lacks the permission. Every list/aggregate query is scoped with `accessibleSites`/`scopeSiteIds` (which takes a permission, e.g. exports use `"report:export"`). Client code imports `can()` from `lib/permissions` only to hide controls.
- **Approvals** (`data/expenses.ts`, rules in `data/expense-rules.ts`): `expenses.status` is draft → pending_approval → approved, or pending_approval → rejected → pending_approval. It's set only by the server: anyone with `expense:direct` (owner, accountant, engineer) is approved at once (`enteredApproved`, reviewed by themselves); an assistant's entry is a draft, or pending when sent with `submit`. Site owners (`expense:approve`) review in `reviewExpense` (row locked, so a second reviewer gets "already approved"); nobody reviews their own entry; rejecting needs a reason. An approved entry that someone else reviewed can't be edited or deleted by anyone; `reopenExpense` sends it back (rejected, with a reason) for the author to correct and resubmit. Drafts are visible only to their author; pending/rejected also to approvers and `expense:edit_any`. Submitting notifies the site's approvers and reviews notify the author (`data/notifications.ts`, written in the same transaction). Receipts follow their expense (`mayView`/`mayManage`), so the receipt route can't be used to read other people's files.
- **People and accounts** (`data/accounts.ts`): there is no public sign-up (Better Auth `disableSignUp` plus `disabledPaths`; `/sign-up` only explains this). The organization owner is the one permanent admin (`isAdmin`/`requireAdmin`; unique index `organization_members_one_owner`, and triggers in migration 0013 refuse removing, demoting or deactivating them). Only the admin creates accounts on `/engineers`: name, email (unique, lowercased), sites, each given the `assistant` role. Nobody sets someone else's password: `password_links` are one-time links (SHA-256 stored, 48 h, a new one revokes older ones) used at `/set-password/[token]`; using one hashes with Better Auth's hasher and deletes the user's sessions. Deactivating (`users.deactivated_at`) deletes sessions and links; `loadActor` and the session-create hook in `lib/auth.ts` refuse deactivated users. The admin itself is created once by `npm run admin:bootstrap` (`src/db/admin.ts`, `ADMIN_EMAIL`/`ADMIN_NAME`/`ORGANIZATION_NAME`); `npm run admin:reset-link` recovers it. Site owners manage roles of people already on their own sites; only org owners/admins grant site ownership or change their own access. A user in several orgs acts in the one they last selected (`organization_members.selected_at`). The old `invitations` tables are kept for their data but nothing uses them.
- **Money**: `numeric(14,2)` stays a string through the server; sums happen in SQL. Convert with `num()` (`data/shared.ts`) only when building display DTOs. `expense_items.amount` is a generated column; `expenses.total_amount` is set from items in the same transaction. Every read of spend must exclude soft-deleted (`deleted_at`) and unapproved (`status <> 'approved'`) expenses: use `countedExpense`/`expenseConditions` in Drizzle, or `e.deleted_at is null and e.status = 'approved'` in raw SQL. Any new insert into `expenses` must set the review columns (spread `enteredApproved(actor)`), or the status checks reject it.
- **Dates**: business "today" is `today()` in `data/shared.ts` (IST; `APP_TODAY` pins it in tests). The client gets it from `useSession().today`; never call `new Date()` for business dates in components.
- **Session context** (`src/lib/session.tsx`): filled by `src/app/(app)/layout.tsx` with user, org, preferences, visible sites with roles, worker/supplier names and the overdue-bill count. Use `useFormat()` for money/dates, `useWritableSites()`/`useManagedSites()`/`useCanManageOrg()` or `can(site.role, …)` to hide controls the server would reject.
- **Spend is counted once, in `expenses`.** Everything else is quantity or liability:
  - Material purchases (`data/materials.ts`) paid now link one `source = "purchase"` expense. On credit they link a supplier bill instead, and only its payments become expenses. Usage moves stock only. Stock = non-voided purchases − non-deleted usage, checked under an advisory lock. Voiding soft-deletes the expense, or deletes the unpaid bill.
  - Labour (`data/labour.ts`): attendance is *earned* (the wage is priced on the server from the day rate × 1/½/0). Labour expenses naming a worker are *paid*, with `labour_kind` wage or advance. Balance = earned − paid per worker per site. Wage payments can't exceed what's owed.
  - Supplier balances (`data/suppliers.ts`) are bills − payments from `billsQuery`; cash purchases are reported apart and never owed.
- **Analytics** (`data/analytics.ts`, dashboard and site budgets) are SQL aggregates over `scopeSiteIds`. *Spent* means expenses. *Committed* is as of today: unpaid bill remainders plus positive wage balances, never the paid part. *Payment kinds* split spent exclusively (bill payment, then purchase, then advance, then wage, then other) and must add up to it. Budget lines (`site_budgets`, category null = the site's total) carry `alert_percent`. Over 100% is always an alert. `test/analytics.test.ts` checks every figure against hand-summed sample records; update it when definitions change.
- **Downloadable reports** (`src/server/reports/`, `GET /api/reports/download`): `build.ts` turns `exportFilters` into a format-neutral `Report`, and every amount, subtotal and total in it comes from SQL. `xlsx.ts` (exceljs) and `pdf.ts` (pdfkit) only lay it out. Only sites with `report:export` are included; consolidated means every such site. Each report applies only the filters that fit it (`APPLIES`) and lists the rest as "not applied". User text goes through `safe.ts`: `safeSheetText` against formula injection, `cleanText` for controls and bidi. Reports are labelled internal statements, never tax invoices. GST is never computed; a supplier GSTIN is shown only if it was recorded. PDFs embed the OFL fonts in `src/assets/fonts` (Carlito for Latin and ₹, Rachana for Malayalam). `MAX_ROWS` refuses oversized reports with a request to narrow them.
- **Invoices** (`data/invoices.ts`, `/invoices`, PDFs in `reports/invoice-pdf.ts`): for `finance:manage` (owners/admins, accountants). *Client invoices* bill the site's client: numbered per org and Indian financial year (`INV/2026-27/0001`, under an advisory lock) unless a number is given; items like expense items; status (unpaid/overdue/paid/cancelled) derived in SQL by `invoicesQuery`: paid once the balance (total − net client payments) reaches 0, overdue past the due date otherwise, part paid or not. They're never edited: cancel (with a reason) and issue a new one; one with money received can't be cancelled until it's refunded or reversed. The old `paid_on`/`paid_method` columns are historical only (migration 0016 copied them into `client_payments`). They are receivables, so they never create expenses or touch spend/budgets. GST here is the one exception to "never computed": a rate the user picks (0/5/12/18/28) applied to the subtotal in SQL; the document says "Invoice", not "Tax invoice" (the org has no GSTIN on record). *Labour invoices* are not stored: `labourInvoice` builds a worker's period on a site from attendance and labour payments with the same definitions as `balancesQuery` (closing = balance at the period's end) and is labelled an internal statement. PDFs: `/api/invoices/client/[id]` and `/api/invoices/labour?site&worker&from&to`, rate-limited with report downloads.
- **Client payments and receipts** (`data/client-payments.ts`, `/receipts`, PDFs at `/api/invoices/receipts/[id]`, `?inline=1` to view/print): for `finance:manage`. `client_payments` is an append-only ledger against client invoices: a trigger (migration 0016) refuses updates and direct deletes (cascades from the invoice/site/org still work). `kind` payment (numbered `RCT/2026-27/0001`), refund or reversal (`RFD/…`, `related_id` = the payment, reason required). Refunds give back up to what's left of one payment; a reversal undoes all of it, once, and only if nothing was refunded; both need `payment:refund` (site owners, org owners/admins). Paid = payments − refunds − reversals; balance = invoice total − paid; a payment can't exceed the balance (no overpayment/credit). Each receipt's "paid before", "paid to date", "balance after" and stage (advance/part/final) come from window sums by `seq` in `ledgerQuery`, so re-downloading gives the same document. Writes lock the invoice row, then the org's receipt advisory lock for numbering; `clientKey` (unique per org) makes a repeated submit return the same receipt. Rendering a PDF never writes. Income only: never expenses or spend. Company details on the letterhead are `organizations.address/phone/email/website`, edited by org owners/admins in Settings.
- **Receipts and bill files** (`data/receipts.ts`, `server/files.ts`, `server/storage/`): bytes are checked by content (`inspectUpload`). PDFs with JS, launch actions or embedded files are refused; JPEG EXIF (GPS) is stripped. Objects are stored under opaque keys, S3/R2 (`STORAGE_DRIVER=s3`) or local in dev. They're only reached via `/api/receipts/[id]`, which checks access and redirects to a 5-minute signed URL (S3 presign, or an HMAC token for `/api/files/[token]`). Replace and remove soft-delete the row (who, when, why) and delete the object. Duplicates (same sha256, or the same supplier and bill number) are flagged with `duplicate_of_id` and never auto-removed. OCR (`receipt-ocr.ts`) only stores suggestions in `ocr`; `confirmed` is what a person entered, and records are never changed from either.
- **Audit**: `audit(tx, actor, …)` (`data/audit.ts`) appends to `audit_log` inside the write's transaction. Every write in materials, labour, suppliers, bills and expenses calls it. Nothing updates or deletes audit rows. It's readable with `audit:read` (site owners, accountants); org-wide rows are for org admins.
- **Bills**: status is derived in SQL (`billsQuery` in `data/bills.ts`). `recordPayment` locks the bill row and creates a linked `bill_payment` expense; those expenses are not editable directly.
- **Auth**: Better Auth (`src/lib/auth.ts`, Drizzle adapter with plural table names). `src/proxy.ts` only does an optimistic cookie redirect; real checks are server-side. After sign-in the admin (and anyone who reads site records) goes to `/`, an assistant engineer to `/my`. Redirect targets (`?next=`) go through `safeNext` in `actions/auth.ts`.
- **Categories:** the order in `CATEGORIES` (`lib/types.ts`) and `CATEGORY_META` (`lib/categories.ts`) is the validated colour order for the `--cat-*` chart tokens. Never re-sort categories before assigning colours.
- **Voice entry:** the browser's Web Speech API (`ml-IN`/`en-IN`) produces text only after the user accepts the notice (`users.voice_consent_at`). `parseVoice` (`data/voice.ts`) turns text into `VoiceDraft`s (`lib/voice.ts`) with Claude (`server/voice-ai.ts`, only when `ANTHROPIC_API_KEY` is set and the user consented; `groundEntries` drops any value not found in the transcript) or the rule-based `lib/voice-parser.ts` (English, Malayalam script, Manglish; also the offline fallback in the browser). Unsaid fields stay null and `draftIssues` blocks saving until the user answers. `saveVoice` re-checks everything, refuses unacknowledged likely duplicates, and is idempotent per `clientKey` (`voice_batches`).
- **PWA, offline and mobile** (details in `docs/mobile.md`): the manifest is `src/app/manifest.ts`. `public/sw.js` caches only `/_next/static`, icons and `offline.html`, never pages or data. Every page and API response is `private, no-store` (`next.config.ts`); keep it that way. The active site is the `active_site` cookie (`useActiveSite`, `activeSiteCookie()`); always check access before using it. Unsynced voice drafts live in `lib/offline-drafts.ts`, keyed per user and org. They're removed only after the server confirms the save, or when the user discards them; syncing reuses the draft's `clientKey`. Client submits use `useSubmitGuard` (ignores double taps) and `useSlowNotice`/`submit()` (slow-network notice). Never show "saved" before the server answers ok. `npm run e2e` runs Playwright against a production build and the test DB.
- **Rate limits** (`src/server/rate-limit.ts`, table `request_limits`): fixed windows counted atomically in Postgres, so all serverless instances share them. Server actions call `auth.api.*` directly, which skips Better Auth's own limiter (that one covers `/api/auth/*`, table `rate_limits`), so sign-in and password links are limited in `actions/auth.ts`. Also AI reads per user (voice falls back to the rule-based reader; OCR refuses) and report downloads. Off under vitest unless `RATE_LIMIT=on`; e2e sets `RATE_LIMIT=off`.
- **Monitoring** (`src/server/monitoring.ts`, `src/instrumentation.ts`, `src/instrumentation-client.ts`): `reportError` logs one JSON line and forwards to Sentry when `SENTRY_DSN` is set. Never put request bodies, query strings or amounts in reports. Unexpected action errors are reported from `actionError` via `after()`. `register()` refuses to start a production server with bad config (`src/server/env.ts`).
- **Uploads** are capped at `MAX_RECEIPT_BYTES` (4 MB, `lib/types.ts`) because Vercel rejects bodies over 4.5 MB; `serverActions.bodySizeLimit` matches. Client pickers go through `prepareFile` (shrinks large photos). Production on Vercel must use `STORAGE_DRIVER=s3`. Deployment and backups: `docs/deployment.md`, `docs/backup-and-recovery.md`.
- **Theme:** `lib/theme-script.ts` is injected into `<head>` and sets the `.dark`/`.light` class before hydration. `lib/theme.tsx` is the runtime provider.

## Styling and UI

- Tailwind v4 with no config file. Theme tokens (white and forest green, category colours) and the custom utilities (`.surface`, `.surface-raised`, `.glass-bar`, `.lift`, `.brand-fill`, `.brand-sheen`, `.num`, `.no-print`) are in `src/app/globals.css`, along with print styles for reports.
- `src/components/ui/*` are shadcn components using the `base-nova` style, built on `@base-ui/react` (not Radix). Add new ones with the shadcn CLI so they match. Icons come from `lucide-react` and charts from `recharts` (`components/charts.tsx`).
- The brand mark is `src/assets/arcadia-mark.png`, rendered by `components/logo.tsx`. `app/icon.png` and `app/favicon.ico` are generated from the same mark.
